# M0 parity contract ownership matrix

This matrix closes the M0 design-accountability requirement for the proposed concepts in
[`CMUX_PARITY_IMPLEMENTATION_SPEC.md`](CMUX_PARITY_IMPLEMENTATION_SPEC.md). It assigns planning
ownership; a row does not make an unimplemented contract public. Any process, protocol,
persistence, authentication, or trust-boundary change still requires its milestone ADR/RFC.

| `WorkspaceGroup`             | Core + workspace runtime; SQLite durable intent                        | Service mutation boundary                          | Additive DTO under `workspace-groups-v1`; ordered migration                            | Core ordering properties, migration/recovery, protocol parity, E2E      |

## Cross-contract rules

- Rust wire types remain canonical; generated TypeScript and strict Zod validate all untrusted data.
- Capabilities use lowercase kebab-case with a `-vN` contract generation. Advertising a capability
  means its complete required command/event set is available.
- Durable changes are ordered transactional migrations with backups and corruption tests.
- CLI JSON output has an explicit schema version and stable exit/error codes.
- Renderer projections never establish durable success. Electron-owned work requires a leased,
  capability-scoped provider rather than generic IPC.
- Every collection, string, payload, queue, replay window, timeout, and retained history requires an
  explicit bound before implementation.
